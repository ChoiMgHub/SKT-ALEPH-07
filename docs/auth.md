# 과제 7 인증 구현 기록 — 로컬 검증 단계

이 문서는 현재 구현과 검증 범위를 설명한다. 공개 배포 확인, 사용자 본인의 두 계정 시험,
5일 실제 사용, 최종 제출 증거까지 완료했다는 보고서가 아니다.

## ① 무엇으로 인증을 붙였는가

자체 회원가입·로그인 처리와 D1 서버 세션을 구현했다. 암호 알고리즘은 직접 만들지 않고
Workers Web Crypto의 HMAC·PBKDF2·난수 생성 기능과 `node:crypto`의 `timingSafeEqual`을 사용한다.
구현 식별자는 `task07-auth-v1`, 프로젝트 런타임 기준은 호환 날짜 `2026-10-21`,
도구 설정은 Wrangler `^4.152.0`이다. 독립 인증 서비스나 별도 인증 npm 라이브러리는 사용하지 않는다.
새 계정은 영문·숫자·밑줄·하이픈 아이디로 생성하며, 앞뒤 공백 제거와 소문자 정규화로 중복을 검사한다.
회원가입 뒤 로그인 폼에서 로그인한다. 공개 첫 화면에는 로그인·가입 폼이 나온다.

## ② 왜 이 방식을 선택했는가

과제 6의 Workers·D1 구조를 이어 쓰면서 저장된 해시, 로그인 상태의 만료·무효화,
서버의 소유자 검사를 코드와 DB에서 설명할 수 있도록 AI가 제안하고 구현한 선택이다.
검토한 대안은 Supabase Auth 같은 관리형 인증 서비스다. 별도 서비스 설정과 데이터 연결을
추가해야 하므로 현재 단계에서는 기존 D1 기반 자체 인증을 선택했다.
자체 인증은 보안 검토와 운영 책임이 더 크며, 이 선택이 관리형 서비스보다 일반적으로 안전하다는 뜻은 아니다.

비밀번호 처리는 다음 순서다.

1. 서버 비밀값 `AUTH_PEPPER`를 키로 HMAC-SHA-256 전처리한다.
2. 계정마다 안전한 난수 소금값 16바이트를 생성한다.
3. PBKDF2-HMAC-SHA-512를 100,000회 적용해 32바이트 결과를 만든다.
4. `pbkdf2-sha512$100000$소금값의16진수$결과의16진수` 형식으로 저장한다.

같은 비밀번호도 소금값이 달라 다른 저장값이 된다. 소금값과 알고리즘은 비밀이 아니며,
pepper는 DB·브라우저·Git에 넣지 않는다. 이 구현은 PBKDF2를 한 번의 일반 SHA 해시로 대체하지 않는다.
설정된 반복 횟수는 아래 ⑥의 제한을 반드시 함께 읽어야 한다.

세션은 32바이트 난수이며, 원본은 `HttpOnly; SameSite=Strict` 쿠키로 전달한다.
HTTPS에서는 `Secure`와 `__Host-` 이름을 사용한다. 로컬 HTTP의 localhost/127.0.0.1에서만
개발용 쿠키 이름을 사용한다. DB에는 원본 세션의 SHA-256 값만 저장한다.
높은 엔트로피의 무작위 세션 조회 키를 해시하는 것은 사용자의 비밀번호를 단순 해시하는 것과 용도가 다르다.
세션 수명은 로그인부터 고정 24시간이며 `expires_at > now`인 경우만 유효하다.
로그아웃은 해당 세션 행을 삭제하고, 비밀번호 변경은 계정의 모든 세션을 삭제한다.
로그인 검증 도중 비밀번호가 바뀐 경우 이전 검증 결과로 세션을 생성하지 않도록 DB 삽입 조건도 확인한다.

## ③ 소스에서 무엇을 바꾸었는가

| 위치 | 역할 |
|---|---|
| `src/auth.js` | 표준 API 기반 비밀번호 처리, 가입·로그인·로그아웃·세션·만료·변경·CSRF·간단한 요청 제한 |
| `src/worker.js` | 로그인 선행 확인, 모든 목록의 계정 범위 제한, 개별 자료 소유자 확인, 계정 삭제 |
| `src/import.js` | 로그인한 계정으로 백업 가져오기, 검증과 트랜잭션, 중복 방지, 원본·ID 대응표 보존 |
| `schema-auth.sql` | users, sessions, plan_owners, auth_attempts, imports 테이블과 인덱스 |
| `public/index.html`, `public/app.js` | 로그인 첫 화면, 가입·로그아웃·비밀번호 변경·가져오기·계정 삭제 화면 |
| `scripts/setup-local.mjs` | 비밀값을 출력하지 않고 로컬 설정 생성, 기존 비밀값 유지 |
| `test/auth.test.js` | 인증·양방향 자료 분리·세션 무효화·가져오기·삭제·UI 회귀 검증 |

소유자 관계는 `plan_owners(plan_id, user_id)`에 둔다. 할 일과 그 실행·완료 이력은
연결된 계획의 소유자를 따른다. 서버가 쿠키의 세션에서 얻은 사용자 ID를 사용하며,
URL·헤더·본문으로 전달한 소유자 값으로 권한을 부여하지 않는다.
대상 자료가 없거나 다른 계정의 자료이면 404를 반환한다. 비로그인 API 접근은 401,
다른 출처 또는 필수 사용자 정의 헤더가 없는 쓰기 요청은 403이다.
목록뿐 아니라 개별 계획·할 일 조회, 수정·삭제, 다른 계획으로 이동, 실행·회고 연결도 검사한다.
같은 실행 요청 번호를 두 계정에서 사용해도 충돌하지 않도록 DB 요청 번호를 계정 범위로 구분한다.

기존 DB의 미할당 자료를 첫 가입자에게 자동 귀속하지 않는다. 과제 6 백업 JSON을
본인이 선택해서 가져온다. ID는 새로 매핑하고 원본 JSON과 대응표를 저장하므로 원본과의 연결을 추적할 수 있다.
가져오기는 파일 2MB·전체 기록 500건까지이며 잘못된 연결 관계는 전체를 취소한다.
같은 계정이 같은 파일을 다시 가져오면 중복 생성하지 않는다.
내보내기는 본인 자료·삭제 이력·가져온 원본과 대응표를 포함하며 비밀번호·pepper·세션은 포함하지 않는다.
계정 삭제는 계정과 연결된 계획·할 일·실행·회고·완료·수정 이력·가져온 원본·세션을 삭제한다.

## ④ 어떤 허용·거부를 확인했는가

AI 작업 환경의 자동 테스트는 기존 12개와 인증 관련 10개를 합쳐 22개다.
각 테스트 계정은 자동 생성한 합성 자료이며 사용자 본인의 실제 5일 사용 기록이 아니다.
테스트는 값을 메모리 안에서 만들고 실제 비밀번호·pepper·세션을 출력하지 않는다.

| 허용 요청 | 대응하는 거부·불변성 확인 |
|---|---|
| 가입 201, 정상 로그인 200 | 정규화한 중복 아이디 409; 없는 사용자와 틀린 비밀번호 모두 같은 401 문구 |
| 본인 자료 조회 200 | 비로그인 목록·내보내기·계정 API 401; 비로그인 `/diary`는 로그인 화면으로 303 |
| 본인 할 일 수정·삭제 200 | A→B와 B→A의 조회·수정·삭제 404; 피해 계정 전체 컬렉션의 행 수·내용 동일 |
| 본인 계획 아래 할 일·실행·회고 저장 | 다른 계정의 계획·할 일에 생성·연결 404; 위조 소유자 값으로 귀속 변경 불가 |
| 유효 세션으로 조회 200 | 로그아웃 후 같은 쿠키 재전송 401, 만료 정각 401 |
| 새 비밀번호 로그인 200 | 변경 전 모든 세션 401, 이전 비밀번호 로그인 401 |
| 본인 백업 가져오기 201 | 중복 가져오기 추가 행 없음, 잘못된 백업 전체 취소, 다른 계정 목록에 노출 없음 |
| 본인 계정 삭제 200 | 이전 쿠키 401, 관련 자료 삭제, 다른 계정 자료 동일 |

Node·SQLite·jsdom 테스트와 별도로 `scripts/runtime-smoke.mjs`가 실제 workerd·D1에서
가입·로그인·인증된 API/페이지·익명 거부·로그아웃 재전송을 확인한다.
이 검사는 배포된 Cloudflare 서비스의 CPU 한도·시크릿 설정·네트워크까지 검증한 결과는 아니다.
평가용 최종 증거는 사용자가 실제 계정 두 개로 시험하고 민감값을 가린 요청·응답 쌍,
저장된 해시 값, 행 수와 내용 비교를 추가해야 한다. 현재 이 문서는 그 현장 증거를 대체하지 않는다.

## ⑤ AI에게 맡긴 일과 내가 직접 한 일

- AI가 한 일: 소스 검토, 인증 방식 제안, 코드·테스트·이 문서 초안 작성과 AI 환경 검증.
- 사용자가 직접 완료한 일: 과제 6 JSON 백업, 별도 작업 폴더·브랜치·저장소 생성과 연결,
  패키지 수정 명령 실행·업로드, 별도 D1 생성, 설정 변경·업로드, 기존 앱의 로컬 DB 생성·실행 확인.
- 아직 사용자가 직접 확인했다고 쓰지 않은 일: 새 인증 코드의 로컬 시험, 배포 확인,
  실제 계정 간 접근 차단 증거 수집, 5일 실제 사용과 중간 계획 변경.
- 사용자의 선택 이유나 AI 제안을 거절한 경험은 임의로 만들어 적지 않는다. 최종 제출 때 실제 판단으로 보완한다.

## ⑥ 남은 문제와 보호 범위

1. PBKDF2-HMAC-SHA-512 100,000회는 OWASP의 현재 권장 220,000회보다 낮다.
   Workers 실행 환경과 비용을 고려한 현재 구현값이며, 별도 pepper를 추가했어도 이 차이를 없애지는 않는다.
   배포 환경의 지원·CPU 시간을 확인하고 더 강한 설정이나 관리형 인증 서비스로 개선해야 한다.
   이 과제용 구현을 민감 자료를 보관하는 상용 인증 시스템으로 소개하지 않는다.
2. pepper를 잃거나 교체하면 기존 비밀번호 검증이 불가능하다. 값은 비공개로 안전하게 보관해야 한다.
   자동 복구·이메일 재설정·MFA·이메일 소유권 인증은 구현하지 않았다.
3. IP별 10분 60회 제한은 간단한 방어이며 분산 공격을 완전히 막지 못한다. 로그인·가입을 합산한다.
4. 가져오기는 원본 파일 소유권을 기술적으로 증명하지 못한다. 본인 백업만 가져와야 한다.
   기존 미할당 자료를 임의의 첫 가입자에게 자동 부여하는 경로는 만들지 않았다.
5. 공개 배포, 시크릿 주입, 사용자의 두 계정 시험, 실제 5개 날짜 기록과 2일 뒤 계획 변경,
   같은 지표의 계산 검증, 최종 6항목 설명·요청 응답 증거·제출 양식은 다음 단계다.
   필수 검증을 수행하지 않은 상태를 이 제한 목록으로 통과 처리하지 않는다.

참고: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html),
[Cloudflare Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/),
[Workers CPU 한도](https://developers.cloudflare.com/workers/platform/limits/).

## 로컬에서 확인하기

실행 중인 개발 서버를 Ctrl+C로 종료한 뒤 PowerShell에서 실행한다.

```powershell
git pull --ff-only
npm.cmd run setup:local
npm.cmd run db:local
npm.cmd test
npm.cmd run dev
```

브라우저에 출력된 로컬 주소를 열어 새로고침한다. 로그인·가입 화면이 먼저 보여야 한다.
새 테스트 아이디 두 개와 다른 서비스에서 쓰지 않는 비밀번호를 준비한다.
같은 비밀번호로 두 계정을 가입시키면 서로 다른 소금값의 검증도 할 수 있다.
실제 비밀번호·쿠키·pepper를 채팅이나 제출 자료에 붙여 넣지 않는다.
로그인한 주 계정에서만 과제 6 백업 JSON을 가져오고, 다른 계정에 보이지 않는지 확인한다.

`setup:local`은 `.dev.vars`와 `.private/worker-secrets.json`을 만들고 기존 키를 유지한다.
두 경로는 Git에서 제외된다. 원격 배포에는 별도의 시크릿 등록 단계가 필요하며,
현재 이 안내에서는 원격 DB 적용·배포를 실행하지 않는다.
